# Anonymous usage statistics

**What it is.** The app keeps a log of what it does in `Data/logs/usage.jsonl` (one JSON line per event) and - with *Settings › Usage statistics* on, which is the default - sends the lines not yet sent to the shop's site (`POST mazesta/v1/usage`, no key) a few minutes after start, every ten minutes, and when the app ends. The switch is the owner's: off means nothing is sent and nothing runs; the local log is still written (it is the user's own record, and it is what they can read to see what would be sent).

**What is in it.** `app.start` (version, edition, language) · `test.run` (test id, outcome, seconds, errors) · `bench.run` (benchmark id, status, seconds, its metrics, its options with the card by name) · `tuning.auto` (undervolt / overclock / overclock plus: verdict, reason key, detail, settings found, and the stock and tuned measurements: clock, peak clock, power, temperature, voltage, score; the scene and memory figures) · `tuning.scene` (the scene test) · `tuning.apply` · `ai.ask` (the model id and whether it opened a chat - **never the question or the answer**). With each post: the installation's random id (`Data/config/usage.json`, made at first use, tied to nothing), the app version, the edition and language, and the parts' names: processor (with cores and threads), graphics cards and the driver's version, the board's model, RAM in GB and each module's size and speed, the drives' models and sizes, Windows version. A `test.run` and a `bench.run` also carry a `sensors` block - what the machine itself measured over the run: processor and card temperature, clock and power (average and peak), left out where it reported none.

**What is never in it.** The user's name, the computer's name, files, folders, addresses, serial numbers, MAC addresses, anything typed. A value that was not measured is left out, not sent as zero.

**On the site** (Mazesta Connect 2.0: *نمای کلی*, *سیستم‌ها* with a page of full specifications per system, and *رویدادها* with filters and paging; before 2.0 one tab *آمار استفاده*): installs (total, active in 7 and 30 days), versions, graphics cards, processors, RAM, benchmark and test runs by status, undervolt/overclock results by kind with the reasons they failed and the average temperature and power saved, assistant use. The sender's address is used only to limit a post count (sixty an hour) and is not stored. Events are kept in monthly files in `wp-content/mazesta-connect-data/`; the dashboard reads the last two months.

**Code.** `Mazesta.Persistence/UsageLog.cs` (the file, the id, the sent mark) · `Mazesta.Desktop/Services/UsageRecorder.cs` (what is recorded; `UsageData` builds each event) · `Mazesta.App/UsageUploader.cs` (the sender) · the plugin's `rest_usage`.

**Messages back to the app.** The same random id is used to ask the site for messages (`GET mazesta/v1/messages`, every eight hours, three times a day at most, only while the statistics switch is on): see `Mazesta.App/MessageInbox.cs` and the plugin's `class-mzc-messages.php`. Nothing but the id and the number of the newest message held goes out.

**The app's own log (0.15.1, Connect 2.7.0).** With the same switch the app also sends its log (`Data/logs/mazesta-web-*.log`, the part not sent yet, up to 192 KB a piece) and Windows Error Reporting's records of Mazesta's own crashes (`Sig[n]` of `AppCrash_Mazesta*`: faulting module, exception code, offset) to `POST mazesta/v1/logs`, so a crash on a computer whose user never sends a diagnostics file can still be found. The profile folder's path and the computer's name are replaced (`%USERPROFILE%`, `%COMPUTERNAME%`) before it leaves. Where it got to is in `Data/config/logsend.json`. Code: `Mazesta.Persistence/LogShipper.cs`. The site keeps logs 90 days and shows them on each system's page.

**Storage on the site (Connect 2.7.0).** The statistics live in three tables of WordPress' own database (not the CRM's second database): `{prefix}mzc_systems` (one row per installation, with `hw`, every part's name in lower case, for the hardware search; `ack`, the newest message it holds), `{prefix}mzc_events` (indexed by time, system, kind and card) and `{prefix}mzc_logs`. On the first call after the update the old files (`installs.php`, `acks.php`, `usage-YYYY-MM.log.php`) are read in once and left in place. Pages: *سیستم‌ها* (search by any part: "3060", "5900HS 32 GB"; "پیام به این N سیستم"), *رویدادها*, *آندرولت و اورکلاک* (per card model: runs, success, median offset / cap / power and the change in temperature, power, clock and scene FPS; then every run with stock → tuned figures), *پیام‌ها* (to all, to chosen systems, or to a group = a hardware search, matched when each system asks, so a system that joins later gets it too).

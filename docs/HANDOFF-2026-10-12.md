## 1. VRAM test: heavier load, more memory, new figures

**What changed** (`src/Mazesta.Diagnostics.Gpu/GpuVramExecutor.cs`):
- Each pass (verify every buffer, then rewrite it) now goes to the card as one submission, and the error count is read back once per pass. Before, the CPU waited after every 256 MiB buffer, so the memory sat idle between buffers.
- The budget is now 95 % of free VRAM minus 384 MiB (it was 90 % minus 512 MiB). Without the free-VRAM sensor it is 80 % of dedicated memory (was 60 %). It is capped at 95 % of DXGI's resident budget (was 90 %).
- The result shows the measured bandwidth (GB/s), the highest and average VRAM temperature, the memory clock, and the memory controller load.
- VRAM temperature is now also in the GPU stress tests and the 3D scene test.
- The diagnosis judges the VRAM temperature. It is Attention from 96 °C and Problem from 104 °C (GDDR6X slows itself near 110 °C). See `GpuCheck.VramWarm/VramHot` and FindingCode `GpuVramHot/Warm/Ok`.

**To verify on the RTX 3090:**
1. Run `gpu.vram` for 10 min with the monitoring page open. The owner saw 106 °C VRAM in another tool, 96 °C in FurMark and only ~86 °C in Mazesta before this change. Expect the VRAM temperature to reach FurMark's level or higher.
2. Check in the result how many MiB were tested; with ~3 GB in use, about 19-20 GB of the 24 GB is expected. Also check the bandwidth figure; something in the 600-850 GB/s range is plausible for 936 GB/s peak.
3. Confirm there is no driver reset (TDR). One submission now holds 2 × (number of buffers) dispatches.
4. If the desktop stutters badly or the driver refuses memory, lower `0.95`/`384` in `GpuVramExecutor.Budget` and update `GpuLogicTests`.
5. Check that the diagnosis card for the VRAM temperature appears under the test's result.

## 2. Video decode and encode (benchmark and two new tests)

**What changed:**
- `src/Mazesta.Diagnostics.Gpu/Benchmarks/Video/*.mp4`: 18 short clips (30 frames each), embedded in the assembly. They are made by `tools/make-video-clips.sh` (ffmpeg): H.264, HEVC, VP9 and AV1 at 1080p, 4K and 8K, 8 and 10 bit, 4:2:0 and 4:2:2. The card decodes these clips, so AV1 is decoded even on cards with no AV1 encoder. Before, the RTX 3090 never decoded AV1 because the stream came from its own encoder.
- `GpuVideoBenchmark.cs` decodes each clip over and over by seeking back to the start, and checks that every pass returns all 30 frames.
  - A frame that is not a Direct3D surface (IMFDXGIBuffer) means Windows decoded it in software, so it is not counted as the card's.
  - Encoding covers H.264, HEVC and AV1 at 1080p and 4K, plus 10-bit HEVC (Main10) and AV1 from P010 input. Each encoded file is played back and its frames are counted.
- New tests `gpu.video.decode` and `gpu.video.encode` (`GpuVideoExecutor.cs`). A lost frame fails the test; a form the card lacks is named in the result.
- The benchmark's version is now 2, its default length is 120 s, and the 4K 8-bit 4:2:0 keys keep their old names.

**To verify (none of the Media Foundation code has run yet):**
1. Run `gpu.video.decode` on the 3090. Expected support on Ampere:
   - Decoded by the card: H.264 8-bit 4:2:0; HEVC 8/10-bit 4:2:0 including 8K; VP9 8/10-bit; AV1 8/10-bit including 8K.
   - Not supported, or "decoded by the processor": H.264 10-bit, and 4:2:2 for H.264 and HEVC. Ampere NVDEC has no 4:2:2; Blackwell (RTX 50) does.
   - If **everything** comes out "not supported", the likely causes are:
     - The seek back to the start: `reader.SetCurrentPosition(Guid.Empty, PROPVARIANT VT_I8=0)` in `Decode`.
     - The output type choice (NV12 / P010 / YUY2 / Y210).
     - `Mf.OnCard`.
2. VP9 needs the "VP9 Video Extensions" and AV1 the "AV1 Video Extension" from the Microsoft Store; HEVC needs "HEVC Video Extensions". If one is missing, the result says "not supported here". Consider a note in the UI telling the user to install the extension.
3. Run `gpu.video.encode`. Check 10-bit HEVC and AV1. If the 10-bit forms fail with an error, check:
   - The profile attribute (`Mf.Mpeg2Profile`, value 2 for HEVC Main10).
   - Whether AV1 needs a profile set too.
4. Run the "Graphics — video" benchmark and check that every figure has a Persian and an English name (keys `Bench_Gpu_Video_Dec_*` / `Enc_*`).
5. Check frame-count honesty: a pass shorter than 30 frames fails the test. If a driver legitimately returns 29 frames (e.g. a dropped first frame after a seek), adjust it, but only with evidence.

## 4. RAM tests take more of the RAM

**What changed** (`src/Mazesta.Diagnostics/Memory/*`):
- Before measuring free RAM, `Win32MemoryProbe.FreeUp` trims the working sets of all other processes (`EmptyWorkingSet`). Their pages move to the page file and come back on use; nothing is closed, so no unsaved work is lost. The owner allowed closing programs, but closing loses work, so trimming was chosen.
- The reserve left to Windows is now max(1.5 GiB, RAM/24); it was max(2 GiB, RAM/10).

**To verify:**
1. On 32/64 GB with a browser open, run `memory.pattern` and note "tested = N MiB" against installed RAM. Expect roughly 85-95 %.
2. Confirm Windows stays responsive and nothing crashes. If the system thrashes, raise the reserve.
3. Note: if there is no page file, trimming frees little.

## Build note (Linux)

`Mazesta.Diagnostics.Gpu` cannot be fully built on Linux: ComputeSharp's shader generator loads kernel32, which gives CS8785 and then CS0315. These two errors are the expected baseline; any other error is new. The projects above it were compiled against a reference assembly of the GPU project. `Mazesta.Core.Tests` passes (426). In `Mazesta.Diagnostics.Tests` the memory tests pass, except the bit-fade test, which needs kernel32 and fails on Linux both before and after these changes.
